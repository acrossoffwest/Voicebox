# Low-latency Phase A: clamp-до-базы + left-context окно + prefill

**Goal:** Снизить структурную задержку пайплайна с ~390–550 мс до ~140–180 мс (при инференсе, влезающем в hop), доказать синтетическим бенчем. Ветка `perf-latency` поверх `bench-latency`.

**Ключевая идея (left-context):** модель получает окно `context + hop`, но наружу уходит только свежий hop. Контекст — уже прозвучавшее аудио, задержки не добавляет; добавляют только hop, crossfade и prefill. Текущая схема — частный случай context == crossfade.

## Решённый дизайн

### Обобщение Pipeline (эмиссия со швом в cf)

Параметры: `window_ms` (вход модели), `context_ms` (перенос между итерациями), `crossfade_ms` (cf ≤ context). `hop = window − context`.

Итерация k, `out` = выход цепочки длиной window (выровнен с входом):
- blend (cf сэмплов): `fade_out * prev_tail + fade_in * out[ctx−cf : ctx]`
- тело: `out[ctx : ctx+hop−cf]`
- `prev_tail = out[ctx+hop−cf : ctx+hop]` (хвост НЕ эмитится — эталон шва следующей итерации)
- эмиссия ровно hop сэмплов; отставание эмиссии от захвата = cf.

При context == crossfade формулы тождественны текущему коду (обратная совместимость проверяется существующими тестами).

### Engine
- carry в `_processor_loop` = `context_samples` (не crossfade).
- clamp двухуровневый: триггер `avail > 2*hop` → срез до `hop` (остаточная задержка после затыка ≈ hop, а не 2*hop).
- prefill = `hop + 2*blocksize` вместо целого окна. Структурная задержка ≈ hop + prefill + cf; инференс T влияет только на запас до underrun (T < prefill − jitter).

### Целевые конфиги (бенч должен подтвердить)
- «низкая задержка»: window 256 / context 192 / cf 24 → hop 64; структурно ≈ 64+84+24 ≈ 172 мс.
- «ультра»: window 240 / context 192 / cf 16 → hop 48; структурно ≈ 48+68+16 ≈ 132 мс.
- Требование к инференсу: T(окно 240–256 мс) < hop устойчиво. Меряется реальным режимом (фаза B).

## Задачи (каждая: тест → red → green → commit)

1. **Clamp-до-базы.** Юнит: порог 2*hop не триггерит дроп при avail ≤ 2*hop; avail > 2*hop → остаётся hop. Бенч-гейт ужесточить: spike `final_ms ≤ steady p95 + hop_ms + 60`.
2. **Pipeline context.** Тесты: (а) context==cf → побайтно совпадает со старым поведением; (б) context>cf: эмиссия hop сэмплов, шов непрерывен на линейном сигнале (identity-chain: выход == вход со сдвигом, допуск 1e-5 вне blend-региона, blend ≤ √2 масштаб); (в) валидация cf ≤ context ≤ window.
3. **Engine carry + prefill.** Бенч-сценарии с context-конфигами; steady p50 в пределах hop+prefill+cf ± 25 мс; underruns == 0 при T = 0.6*hop.
4. **Матрица бенча + EngineConfig + UI/CLI.** Новые поля `context_ms` (default = crossfade_ms для старого поведения). UI (`ui_pipeline._build_config`) и CLI переводятся на 256/192/24. Полный прогон матрицы: старые и новые конфиги в одной таблице — структурный выигрыш виден цифрами.

## Вне фазы
- Реальный режим бенча (torch, инференс-замер) — фаза B, окружение ставится.
- fcpe/fp16/ONNX-ускорения RVC — фаза C, по результатам замера.
